# MEMORY-WEIGHTING.md — 记忆加权模型

> 状态：**模型定稿，未实现**（2026-10-28）。
> 一句话：检索分数不该只看「相关不相关」，还要看**这件事有多重、有多急、熟不熟、完没完**。
> 这份文档只定义模型和边界，不含代码。实现顺序见 §9。

---

## 一、要解决的问题

现在的检索只有一个维度：**文本相关**。所以会出现四种「她不该这样」的情况：

| 现象 | 缺的维度 |
|---|---|
| 三个月前说过的要紧事，问起来想不起来 | **分量**（该记多久） |
| 明天要交的东西，今天不提 | **紧迫**（离 deadline 多远） |
| 天天聊的琐事随口就来，只提过一次的关键信息沉底 | **熟悉度**（用没被用过） |
| 「说了没下文」的事，不会再被提起 | **状态**（完没完） |

四个维度。它们不是四个独立功能，是**同一个强度模型里的四个因子**——落到字段上是七个，见 §2。

---

## 二、七个量

| 量 | 范围 | 来源 | 会不会变 | 管什么 |
|---|---|---|---|---|
| `importance` 内在分量 | 0–3 | 整理会话写入时标注 | **不变** | 这条该记多久 |
| `deadline` 截止时间 | 时间戳 / 空 | 写入时从文本提取，可为空 | 不变 | 用来算紧迫性 |
| `urgency` 紧迫性 | 0–1 | `deadline` 与当前时间算出来 | **每天变** | 现在有多该被想起 |
| `readiness` 准备度 | 0–1 | 整理会话从对话里标注 | 会变（但慢） | 还差多少没做完 |
| `strength` 强度 | ≥0 | 痕迹叠加（见 §3） | **每次使用变** | 熟不熟、刚办完没 |
| `openLoop` 未闭合 | 0/1 | 状态位，由整理会话判定 | 直到关闭 | 完没完 |
| `closedAt` 完成时间 | 时间戳 / 空 | 关闭 openLoop 时写 | 一次性 | 完成后的那段强痕迹 |

**`importance` 是静态的，`urgency` 是动态的。** 这是这份文档最重要的一条：

> 同一场面试，下个月、下周、明天，**内在分量一样，紧迫性不一样**。
> 不需要重新标注——`deadline` 写一次，`urgency` 每天自己算。

## 三、合成

### 3.1 强度

```js
const TAU_USE = 14;                                  // 天
const tau = TAU_USE * (1 + importance);              // 重要的事沉得慢

strength(now) =
    exp(-(now - createdAt) / tau)                    // ① 写下来那一刻的痕迹
  + Σ_i exp(-(now - t_use_i) / tau)                  // ② 每次被采用的痕迹
  + (closedAt ? 2.0 * exp(-(now - closedAt) / tau) : 0)   // ③ 完成那一下的强痕迹
```

三条痕迹都随 `tau` 衰减，而 `tau` 被 `importance` 放大：

| importance | tau | 大约多久沉到 1/e |
|---|---|---|
| 0 | 14 天 | 两周 |
| 1 | 28 天 | 一个月 |
| 2 | 42 天 | 六周 |
| 3 | 56 天 | 两个月 |

**注意**：这里没有「基础分 × 衰减」那种写法。重要性不直接加分，它只**改变衰减速度**——因为「重要」的语义是「记得久」，不是「排得前」。

### 3.2 紧迫性

```js
function urgency(deadline, now, openLoop) {
  if (!deadline) return 0;                       // 没有 deadline 的事不参与
  const days = (deadline - now) / 86_400_000;
  if (days < 0)  return openLoop ? 0.8 : 0;      // 逾期：没办完是欠账，办完了归零
  if (days <= 1) return 1.0;                     // 今天 / 明天
  if (days <= 3) return 0.8;
  if (days <= 7) return 0.5;
  if (days <= 30) return 0.2;
  return 0.05;                                   // 远期
}
```

三场面试的落点：

| 场景 | importance | urgency | 
|---|---|---|
| 下个月的面试 | 2 | 0.2 |
| 下周的面试 | 2 | 0.5 |
| 明天的面试 | 2 | **1.0** |

**到下个月快到时，urgency 自己会升上来。** 时间就是参数，不需要人再动手。

### 3.2b 紧迫性还要乘「还差多少」

只看时间是不够的。同一场面试，明天到期，但**准备充分和没准备不是一回事**。

```js
// readiness: 0 = 完全没准备，1 = 准备充分（由整理会话从对话里标注）
const required = readiness <= 0.33 ? 1.5    // 没底 → 优先级抬高
               : readiness >= 0.75 ? 0.5    // 有底 → 优先级回落
               : 1.0;

urgency_eff = urgency * required;
```

| 场景 | urgency | readiness | urgency_eff |
|---|---|---|---|
| 明天面试，没准备 | 1.0 | 0.1 | **1.5** |
| 明天面试，准备充分 | 1.0 | 0.9 | **0.5** |
| 下个月面试，没准备 | 0.2 | 0.1 | 0.3 |

**同一场考试，没准备时的提醒优先级是准备好了的三倍。** 这符合直觉：提醒的价值取决于「还差多少」，而不是「还剩多久」。

附带收益：准备完的事会**自动降下去**，不会在整个窗口期一直浮在眼前——人准备完了就不想了。

### 3.3 检索分

```js
const BETA  = 0.30;   // 强度微调
const K     = 3;      // tanh 归一化尺度
const GAMMA = 0.40;   // 紧迫加成
const DELTA = 0.50;   // 未闭合加成
const CAP   = 2.5;    // 总乘数封顶

const combined = (1 + BETA  * Math.tanh(strength / K))
               * (1 + GAMMA * urgency_eff)
               * (1 + DELTA * openLoop);

score = baseScore * Math.min(combined, CAP);
```

三个乘数**各管一件事，互不覆盖**：

- `strength` → 熟不熟（沉底了就弱）
- `urgency_eff` → 急不急（时间 × 还差多少）
- `openLoop` → 完没完（状态）

`baseScore` 是门槛：**三个乘数都不能把不相关的事拽上来**。相关性低于下限的命中，三个乘数一律不生效。

**为什么封顶**：三条同时拉满时（未闭合 × 明天到期 × 没准备）乘数会到 3.15 倍，一件没准备的临期悬案会压过库里所有其他记忆。`CAP = 2.5` 是拍的初值，实测再调。

## 四、交互规则

「互相影响」不是四个分数相加，是下面这几条因果关系：

| 交互 | 机制 | 你观察到的效果 |
|---|---|---|
| 分量 → 记忆寿命 | `tau = 14 × (1 + importance)` | 三个月前要紧的事还在，三个月前的午饭已经沉底 |
| 截止 → 紧迫 | 每天重算 `urgency` | 临期的事自己浮上来，不用提醒 |
| 使用 → 强度 | 每次采用加一条痕迹 | 常在嘴边的事更容易被想起 |
| 完成 → 强痕迹 | 关闭时 `+2.0` | **办完的大事记得比说过的琐事久** |
| 未闭合 → 检索 | `× 1.5` | 悬着的事更该被提起 |
| 逾期 + 未闭合 | `urgency = 0.8` | 答应过没做 → 欠账感 |
| 准备度 → 紧迫 | `required = 1.5 / 1.0 / 0.5` | 没准备的事更该被提醒，准备好了的自动降下去 |

**完成不等于清零**：`openLoop` 关闭时会留下一次强度为 2.0 的痕迹（是普通使用的两倍），然后照常衰减。所以「办完的事」比「说过的事」记得久——不是因为重要，是因为它被「完成」这个动作强化过。

## 五、三个时间不能混

同一条记忆涉及三个不同的时间，用途完全不同：

| 时间 | 例子：「下周三面试」 | 用在哪 |
|---|---|---|
| `createdAt` | 今天写下这条记忆的时刻 | ① 基础痕迹的衰减 |
| `t_use[]` | 每次被召回采用的时刻 | ② 使用痕迹 |
| `deadline` | 下周三那场面试 | `urgency` |

写下来的时候可能离事件还有一周。**把 `createdAt` 当成事件时间，紧迫性会算错一周。**

## 六、用词：沉底，不是遗忘

这份模型**不删除任何数据**。`facts/*.jsonl` 是 append-only，衰减只影响排序权重。

| 不说 | 说 |
|---|---|
| 遗忘、忘掉、没了 | **沉底**、退到背景、不再主动浮现 |
| 权重归零 | 沉底（强相关时仍然召得回） |
| 删掉了 | （只有显式 `forget` 才删） |

区别很实在：一条沉底的记忆，你哪天提一个高度相关的词，它照样排得上来。它只是不再「随手就浮上来」。

> 所以衰减是**注意力分配**，不是**数据生命周期**。

## 七、存储与可重建

`reindex --force` 之后所有数值必须与之前一致。这条约束决定了**哪些能存、哪些必须算**。

| 数据 | 存哪 | 可变 | 重建方式 |
|---|---|---|---|
| 原始事实 | `facts/*.jsonl` | 否 | — |
| `importance` / `deadline` | jsonl 元数据字段 | 否 | 直接读 |
| 使用日志 | `touches(id, at, kind)` 表 | **只追加** | 原始数据 |
| `openLoop` / `closedAt` | SQLite `memories` 表 | 是 | 从日志重放 |
| **`strength`** | **不存** | — | **每次按 §3.1 现算** |
| `urgency` | **不存** | — | **每次现算** |

关键：**`strength` 和 `urgency` 永远不落盘**。只要 `importance`、`deadline`、`touches`、`openLoop` 在库里，就能确定性重算。

## 九、落地顺序

一次设计，两个 PR。**不是因为可以分四次，是因为这些量一起上，出问题时排查面是四倍。**

### PR 1 — 地基

- Schema：`memories` 加 `importance`、`deadline`、`open_loop`、`closed_at`
- 整理会话：写入时标注 `importance`（标准见 §10）、提取 `deadline`
- 检索：接上 `urgency` 这一个乘数（`strength` 恒为 0，`openLoop` 恒为 0）
- `?explain=1`
- **可回滚**：纯排序改动，不写任何新数据

上线后能直接看到「重要性 → 衰减速度」和「临期 → 浮上来」这两条对不对。

### PR 2 — 动态

- `touches` 表 + 桥接注入后的 `POST /v1/touch`（fire-and-forget，失败只记日志）
- 整理会话识别 `open_loop`（说了没下文 / 问了没答 / 答应没兑现）
- 关闭时写 `closed_at`（完成强化）
- 接上 `strength` 和 `openLoop` 两个乘数

此时地基已稳，只剩「数值对不对」。

## 十、参数与失败模式

### 10.1 importance 的标注标准

这是整套里最容易做烂的一环。标注含糊 → 全是 2 → 等于没有。

| 值 | 判据 | 例子 |
|---|---|---|
| 0 | 说完就过，明天不会想起 | 「今天下雨了」「刚吃完饭」 |
| 1 | 有点信息量，但不需要记住 | 「那个剧更新了」 |
| 2 | 承诺、偏好、决定、别人告诉我的事 | 「下周把文档收口」「他不吃辣」 |
| 3 | 身份、关系、健康、长期方向 | 「他爸去年做过手术」「我们约定的那件事」 |

标注 prompt 用二选一问句，别让模型自由发挥：

> **这件事如果三个月后忘了，会不会有问题？** 答「会」才给 2 以上。

### 10.1b readiness 的标注标准

同样别让模型自由发挥。判据是「**如果明天就要，他现在够不够**」：

| 值 | 判据 | 例子 |
|---|---|---|
| 0–0.2 | 明确还没开始 | 「还没看」「明天再说」 |
| 0.3–0.6 | 起了个头 / 部分准备 | 「看了一点」「知道个大概」 |
| 0.7–1.0 | 明确说准备好了 | 「刷完了」「差不多了」 |
| 沿用上次 | 没有新信息就别改 | — |

**只从明说里取，不从语气推断。** 「应该吧」「大概吧」不算任何值——那是在猜，不是事实。猜出来的 readiness 会让整条紧迫性失真。

### 10.2 失败模式

跑三个月后如果出现下面两种，正好是对称的：

| 现象 | 说明 | 拧哪个 |
|---|---|---|
| 只记得天天聊的事，重要但冷门的事沉了 | 活跃压过分量 | `BETA` 调小，或 `importance` 标注标准收紧 |
| 老提早就该翻篇的事 | 衰减太慢 | `TAU_USE` 调小，或 `DELTA` 调小 |

**一次只动一个参数**，否则分不清是哪个拧过头了。

### 10.3 副作用：临期扎堆

紧迫性会让同一周到期的几件事一起浮上来，挤满检索结果。

这是真实行为（临期就是占满注意力），但工程上要加闸：**加权后只取 top-K**（建议 K=8），否则上下文会被临期事项塞死。

## 十一、边界：这套东西不做什么

1. **不做主动驱动。** 这些因子只影响「被检索时的排序」，不会让她在没人叫的时候主动说话。
2. **不用数值模拟内在状态。** 没有 `pressure`、没有「渴望值」。所有量记录的都是**发生过的事实**（用了几次、什么时候到期、准备到哪了、完没完），不是编出来的心理量。
3. **不叫「焦虑」。** 这套机制算出来的东西叫 `urgency_eff` / `tension`（该被提起来的程度），不叫 anxiety。它会让人以为「她有压力」，但那只是排序结果，不是感受。**用词一旦滑到情绪，就变成了假装。**
3. **不删除数据。** 衰减只降权。
4. **不改相关性检索本身。** `baseScore` 的门槛高于一切乘数。
5. **不做跨用户学习。** 权重只属于这一份记忆库。
